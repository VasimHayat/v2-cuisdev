A randomly generated password should be at least 16 characters long, or a passphrase of at least 6 random words. At that length, guessing it by brute force is out of reach even in a worst case where an attacker has stolen a database and can test guesses offline. Length matters far more than adding symbols, and "randomly generated" matters most of all.

This guide shows the math behind that advice, so you can judge any password policy yourself. If you just want a strong password now, the [Password Generator](/tools/developer/password-generator/) creates one in your browser and shows its entropy.

## What is password entropy?

Entropy measures how many guesses an attacker needs, expressed in bits. Each bit doubles the number of possibilities. For a password generated at random, it is easy to calculate:

```
entropy in bits = length × log2(size of the character pool)
```

The pool is the set of characters the generator picks from:

| Character pool | Pool size | Bits per character |
| --- | --- | --- |
| Digits only | 10 | 3.32 |
| Lowercase letters | 26 | 4.70 |
| Lowercase and digits | 36 | 5.17 |
| Upper, lower and digits | 62 | 5.95 |
| All printable ASCII | 94 | 6.55 |

So a 16-character password drawn from all 94 printable characters has 16 × 6.55 = 104.9 bits of entropy.

There is one big condition. This formula only describes passwords chosen at random by a computer. A human who picks `Summer2026!` uses the same character types, but attackers try words, names, dates and common substitutions first, so its real strength is a small fraction of what the formula suggests.

## How long does it take to crack a password?

That depends on how fast an attacker can guess, which depends on the situation:

- **Online attacks**, typing guesses into a login page, are slow and usually rate-limited or locked out after a few attempts.
- **Offline attacks**, after a breach, run as fast as the attacker's hardware allows. How fast depends heavily on how the site stored passwords. A fast hash such as unsalted SHA-256 allows billions of guesses per second on modern GPUs. A slow password hash such as Argon2 or bcrypt reduces that dramatically.

To make the numbers concrete, the table below assumes a hard case: 10 billion (10^10) guesses per second, offline. On average an attacker finds the password after searching half the possibilities. These are estimates under that stated assumption, not measurements.

| Password | Entropy | Average time at 10^10 guesses per second |
| --- | --- | --- |
| 8 lowercase letters | 37.6 bits | about 10 seconds |
| 8 letters and digits | 47.6 bits | about 3 hours |
| 8 characters, all printable | 52.4 bits | about 3.4 days |
| 12 lowercase letters | 56.4 bits | about 55 days |
| 12 letters and digits | 71.5 bits | about 5,300 years |
| 12 characters, all printable | 78.7 bits | about 780,000 years |
| 16 characters, all printable | 104.9 bits | far longer than the age of the universe |

Two things jump out. Eight characters is no longer enough for anything important, whatever symbols you add. And adding length helps much more than adding character types: going from 8 to 12 printable characters adds about 26 bits, which multiplies the work by 94^4, roughly 78 million times.

## Why does length beat complexity?

Each extra character multiplies the possibilities by the pool size. Expanding the pool from 62 to 94 characters only raises the bits per character from 5.95 to 6.55, while each extra character adds the full 5.95 or 6.55 bits.

- 12 characters from the full 94-character pool: 78.7 bits.
- 16 characters from just letters and digits: 95.3 bits.

The longer, simpler password wins comfortably. It is also easier to type on a phone keyboard, which matters if you ever have to enter it by hand.

## Are passphrases as strong as random passwords?

Yes, when the words are chosen at random rather than by you. A passphrase's entropy depends on the size of the word list and the number of words:

```
entropy in bits = words × log2(size of the word list)
```

The classic Diceware list has 7,776 words, because each word is chosen by rolling five dice (6^5 = 7,776). Each word adds 12.92 bits:

| Words from a 7,776-word list | Entropy |
| --- | --- |
| 4 | 51.7 bits |
| 5 | 64.6 bits |
| 6 | 77.5 bits |
| 7 | 90.5 bits |

Six random words reach about the same strength as a 12-character random password using every printable character, and something like `glacier-orbit-velvet-pumpkin-harbor-tiny` is far easier to remember and type. Smaller word lists give fewer bits per word, so use a word or two more with them. A generator should tell you the entropy of what it produces.

What matters is that a program picks the words. A memorable phrase from a song or a quote is a guessable string, no matter how long.

## What do the official guidelines say?

The NIST digital identity guidelines (Special Publication 800-63B, 2017 edition) changed password policy for the better. Among other points, they say systems should:

- require at least 8 characters for user-chosen passwords and allow at least 64;
- not impose composition rules such as "one uppercase, one symbol";
- check new passwords against lists of breached and common passwords;
- not force periodic password changes without evidence of compromise.

Later revisions of the guideline have kept moving in the same direction: longer passwords, fewer arbitrary rules. If you are setting a policy for a system, check the current revision. If you are choosing your own password, aim well above any minimum.

## How to generate a strong password in code

Use your platform's cryptographically secure random generator, never `Math.random` or Python's `random` module. In Python, the `secrets` module exists for exactly this:

```python
import math
import secrets
import string

def password(length=16, alphabet=string.ascii_letters + string.digits + string.punctuation):
    return "".join(secrets.choice(alphabet) for _ in range(length))

def entropy_bits(length, pool_size):
    return length * math.log2(pool_size)

print(len(string.ascii_letters + string.digits + string.punctuation))  # 94
print(round(entropy_bits(16, 94), 1))  # 104.9
print(round(entropy_bits(6, 7776), 1))  # 77.5
```

`secrets.choice` picks each character uniformly from the alphabet, so the entropy formula holds exactly.

## Does the website's password storage matter?

Yes, a lot. A site that stores passwords with a slow, salted password hash such as Argon2id, scrypt or bcrypt makes every guess expensive. A site that uses a fast general-purpose hash such as MD5 or SHA-256 makes guessing cheap. You can see how quickly those fast hashes compute in the [Hash Generator](/tools/developer/hash-generator/): speed is a feature for checksums and a weakness for passwords.

You cannot control how a website stores your password, which is the strongest argument for long random passwords. They stay safe even when a site gets it wrong.

## Practical rules for your own accounts

- Use a password manager, so every password can be long, random and unique.
- Generate 16 or more random characters, or 6 or more random words.
- Never reuse a password across sites. Reuse turns one breach into many.
- Turn on two-factor authentication where it is offered, preferably with an authenticator app or a security key.
- Change a password when a service reports a breach, not on a calendar.
