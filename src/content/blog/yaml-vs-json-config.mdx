Use YAML for configuration that people write and edit by hand, because it allows comments and has less punctuation. Use JSON for configuration that programs generate or exchange, because it is strict, unambiguous and supported everywhere. When a file is edited by hand but must be exact, JSON with comments, or YAML with every ambiguous string quoted, gives you the best of both.

If you need to move a config between the two, the [YAML to JSON](/tools/converters/yaml-to-json/) converter shows exactly what a YAML file means once it is parsed. The rest of this guide compares the formats in detail.

## How do YAML and JSON compare?

| | YAML | JSON |
| --- | --- | --- |
| Comments | Yes, with `#` | No (some tools accept JSONC) |
| Structure | Indentation | Braces and brackets |
| Quotes | Usually optional | Required for every string and key |
| Type inference | Automatic, can surprise you | Explicit, no surprises |
| Multi-line strings | Built in (`\|` and `>`) | Escaped `\n` only |
| Reuse within a file | Anchors and aliases | None |
| Multiple documents per file | Yes, separated by `---` | No |
| Parsers | Fewer, and they differ in details | In every language's standard library or close to it |
| Typical uses | Kubernetes, CI pipelines, Docker Compose, Ansible | package.json, API payloads, generated config |

## What is YAML better at?

### Comments

The single biggest reason people choose YAML for config is comments. Being able to write why a timeout is 30 seconds, or which ticket a flag belongs to, right next to the value is enormously useful in a file a team maintains for years. Plain JSON has no comment syntax at all.

### Less noise

The same configuration in both formats:

```yaml
server:
  host: example.com
  port: 8080
  tls: true
```

```json
{
  "server": {
    "host": "example.com",
    "port": 8080,
    "tls": true
  }
}
```

The YAML version has no braces, no quotes and no commas to get wrong. In a file of a few hundred lines, that difference adds up for anyone reading or editing it.

### Long text and reuse

YAML block scalars hold multi-line text, such as a shell script in a CI step, without escaping. Anchors (`&name`) and aliases (`*name`) let you define a block once and reuse it, which keeps repeated settings in sync.

## What is JSON better at?

### No type surprises

In JSON, `"NO"` is a string and `false` is a boolean, because quotes decide. In YAML, unquoted values are interpreted, and the rules changed between YAML versions. Here is the same snippet parsed by the JavaScript `yaml` library in YAML 1.2 mode and in YAML 1.1 mode:

```js
import YAML from 'yaml';

const doc = 'countries:\n  - GB\n  - NO\n  - FR\nversion: 1.10\nenabled: yes\n';
console.log('YAML 1.2:', JSON.stringify(YAML.parse(doc)));
console.log('YAML 1.1:', JSON.stringify(YAML.parse(doc, { version: '1.1' })));
```

```text
YAML 1.2: {"countries":["GB","NO","FR"],"version":1.1,"enabled":"yes"}
YAML 1.1: {"countries":["GB",false,"FR"],"version":1.1,"enabled":true}
```

Three things went wrong without any error message:

- Under YAML 1.1 rules, the country code `NO` became `false`. This is known as the Norway problem.
- `yes` became `true` under 1.1 and stayed a string under 1.2, so the same file means different things to different parsers.
- In both versions, the version number `1.10` became the number `1.1`, losing the trailing zero.

Many widely used parsers still follow YAML 1.1 rules, so you cannot assume which behavior you will get. Our article on [YAML gotchas](/blog/yaml-gotchas/) covers more of these traps.

### Strictness

A JSON file is either valid or not, and every parser agrees on what a valid file means. That makes JSON the safer choice for anything generated by one program and read by another, and for config that is validated in CI.

### Universal tooling

Every mainstream language can read and write JSON with a standard or near-standard library, and the output of one is always readable by another. YAML support is widespread too, but parsers differ in edge cases, schema version and features.

## Is YAML less safe than JSON?

It can be, depending on the library. Some YAML loaders can construct arbitrary language objects from tags in the file, which is dangerous if the file comes from an untrusted source. In Python's PyYAML, for example, use `yaml.safe_load` rather than `yaml.load` for any input you do not control. JSON parsers only ever produce plain data such as objects, arrays, strings, numbers, booleans and null, so they do not have this class of problem.

## Which tools expect which format?

Often the decision is made for you:

- **JSON:** `package.json`, most API request and response bodies, browser extension manifests, many generated lock files.
- **JSON with comments (JSONC):** `tsconfig.json` and VS Code's settings files, which accept comments even though standard JSON does not. See our comparison of [JSON, JSON5 and JSONC](/blog/json-vs-json5-jsonc/) for what each variant allows.
- **YAML:** Kubernetes manifests, GitHub Actions and most CI systems, Docker Compose files, Ansible playbooks, OpenAPI specifications (which also accept JSON).

Because YAML 1.2 is designed as a superset of JSON, many YAML-based tools, including Kubernetes, also accept JSON input. That makes JSON a reasonable choice when you generate those files from code.

## How do you get the benefits of both?

You do not have to choose purely one way.

1. **Write YAML defensively.** Quote any value that could be read as something else: country codes, version numbers, anything with leading zeros, and the words yes, no, on and off. `version: "1.10"` and `country: "NO"` parse as strings everywhere.
2. **Validate with a schema.** JSON Schema works on parsed YAML as well as JSON, so you can check required keys and types in CI regardless of the file format.
3. **Generate YAML from code when it gets big.** If a config is mostly repeated structure, write it as data in a programming language and emit YAML or JSON from that, instead of maintaining hundreds of near-identical lines by hand.
4. **Convert to check meaning.** Converting a YAML file to JSON shows exactly how the parser understood each value. If a string you expected shows up as `false` or a number, quote it.

## A simple rule for choosing

- Edited by people, read by one tool, needs comments: **YAML**, with ambiguous values quoted.
- Generated by code, exchanged between systems, or validated strictly: **JSON**.
- Edited by people but your tool supports it: **JSONC**, which keeps JSON's strictness and adds comments.

When you need to go the other way, for example to turn a JSON API response into a readable YAML fixture, the [JSON to YAML](/tools/converters/json-to-yaml/) converter quotes strings that would otherwise be read back as numbers, booleans or null.

## How do you convert between YAML and JSON in code?

In most languages it is a parse followed by a serialize. In JavaScript, with the `yaml` package:

```js
import YAML from 'yaml';

const text = `# Service settings
server:
  host: example.com
  port: 8080
countries: ["GB", "NO"]
`;

const data = YAML.parse(text);
console.log(JSON.stringify(data));
console.log(YAML.stringify({ server: { host: 'example.com', port: 8080 }, country: 'NO', version: '1.10' }));
```

```text
{"server":{"host":"example.com","port":8080},"countries":["GB","NO"]}
server:
  host: example.com
  port: 8080
country: NO
version: "1.10"
```

Notice two things in the output. The comment is gone, because JSON has nowhere to put it, so converting a hand-written YAML config to JSON and back loses its documentation. And the writer quoted `"1.10"`, which would otherwise become a number, but left `country: NO` unquoted, because under YAML 1.2 rules that is already a plain string. A tool that still follows YAML 1.1 would read that same line as `false`. If files you generate will be read by older parsers, quote values like these yourself, or check how your library's writer handles them.
